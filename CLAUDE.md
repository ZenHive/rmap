# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

`rmap` is a single-binary Rust CLI that manages portable roadmap data (`roadmap/tasks.toml`) for any project, regardless of language. It renders `ROADMAP.md` and `roadmap/data.json` from the TOML source. Since 2026-05-13 rmap drives its own roadmap from `roadmap/tasks.toml` → `ROADMAP.md`; see `DESIGN.md` for the design contract and `AGENTS.md` for additional contributor guidelines.

## Commands

```
cargo build                              # compile
cargo test                               # unit + integration + golden tests
cargo test --test cli                    # run a single test file
cargo test render_command_updates        # run tests matching substring
cargo fmt --check                        # check formatting (rustfmt defaults)
cargo clippy --all-targets -- -D warnings
cargo run -- validate                    # exercise CLI during dev
cargo run -- render --dry
```

Edition is `2024` (Cargo.toml). MSRV: whatever ships with Rust 1.85+.

**Reinstall after any source change.** rmap is dogfooded on itself (`roadmap/tasks.toml` → `ROADMAP.md`), so a stale `~/.cargo/bin/rmap` will silently render with the old schema or reject a TOML using a newly-added field (Phase 12c discovery #2: `[focus]` was rejected by a pre-`schema::Focus` binary). After any change to `src/`, run `cargo install --path .` before invoking `rmap` again — the binary on `$PATH` is what matters, not whatever `target/release/rmap` happens to hold. The smoke test (`cargo test --test skills_smoke`) compiles fresh under cargo and catches regressions in `SKILLS.md` examples regardless of the installed binary, but interactive `rmap` calls do not.

**Prefer `rmap` CLI over direct `tasks.toml` edits for operations that have a mutator.** Today the mutator surface is `rmap status` (single + bulk), `rmap mark`, `rmap depend`, and `rmap new` — those go through `toml_edit` (comments/formatting preserved) and the validate-then-write contract (invalid mutations leave the file byte-equal). Use them when the operation matches. Direct TOML edits are the only path for everything else — bundle CRUD, phase CRUD, focus changes, score/title/AC edits, top-level metadata. After any direct edit, run `cargo run -- validate --check-render` (or `rmap render` then `rmap validate`) before committing so render drift and schema breakage are caught at the source.

## Architecture

Pipeline: `tasks.toml` → `schema::Tasks` → either `render_roadmap_str` (markdown) or `export_json_str` (data.json) → write back. Mutations route through `toml_edit` to preserve user formatting and comments.

Module layout:

- `schema.rs` — `serde` structs with `#[serde(deny_unknown_fields)]` on every type. `TaskId` is an `untagged` enum (`Number(u32) | Text(String)`) so task IDs can be either. Custom `PartialEq<u32>` lets numeric IDs compare directly.
- `validate.rs` — parses TOML into `Tasks`, then runs semantic checks: schema_version, statuses, markers, score-range (`1..=10` on each of `task.scores.{d,b,u}`), assignees, linear_id format (skipped if `[linear]` table absent), timestamp formats (ISO-8601), `blocked_reason` required when `status = "blocked"`, dependency existence, dependency cycles (DFS with back-edge detection), cross-repo relations, phase/bundle reference integrity, and `[focus].phase` matching a declared phase. Errors carry `path:line` location.
- `render.rs` — three passes over the input `ROADMAP.md`, run in order **focus → mermaid → tasks**. Each pass independently matches its own marker pair and replaces ONLY the body between matched markers; bytes outside markers are byte-preserved. **TASKS pass:** byte-cursor walk over `<!-- TASKS:BEGIN phase=N -->` / `<!-- TASKS:END -->` pairs. The phase number is parsed from the BEGIN marker line. Per-task row: `🎁 **<bundle>** · <title>` when no `module` is set; `🎁 **<bundle>** · *<module>* · <title>` when `Task.module` is `Some` — the `module_segment` is an empty string for module-less tasks, so the existing render shape is byte-preserved. **FOCUS pass:** single optional `<!-- FOCUS:BEGIN -->` / `<!-- FOCUS:END -->` pair (no phase parameter). When `[focus]` is set, the body emits three lines: `**Focus phase:** N — <name> (M of K done · J in progress)`, `**Last shipped:** Task A — <title>, Task B — <title> on YYYY-MM-DD` (or `no recent shipments` if no focus-phase task's `done_at` is within `SHIPPED_WINDOW_DAYS = 7`), `**Up next:** Task C — <title> [D/B/U → Eff]` (or `none — focus phase complete or all blocked`). When `[focus]` is absent but markers are present, emits a single `**Focus phase:** not set — add [focus] to tasks.toml` line — keeps the marker honest. Only the first FOCUS pair is replaced; later pairs are left untouched (one-pair convention). **MERMAID pass:** single optional `<!-- MERMAID:BEGIN -->` / `<!-- MERMAID:END -->` pair. Emits a fenced ```` ```mermaid ```` `gantt` block, one `section` per phase (sorted by `phases[*].order`), one row per task with `started_at`. Row shape by status: `done` → `<title> :done, <started_at>, <done_at>` (rows with missing `done_at` are skipped — degenerate); `in_progress` → `:active, <started_at>, <today>`; `blocked` → `:crit, <started_at>, <today>`; `pending` (or missing `started_at`) → omitted. Empty-state body (no qualifying task) collapses to a minimal valid gantt with `%% no tasks with started_at yet`. Title colons / commas / semicolons (`:`, `,`, `;`) are rewritten to em-dash (`—`) at render time because mermaid parses `task :status, start, end` (`,` is the field separator; `;` is reserved for `dateformat`/etc.). Only the first MERMAID pair is replaced (one-pair convention).
- `export.rs` — separate `ExportedTask` struct that adds the computed `eff` field for the JSON output. `eff` is never stored in `tasks.toml` or in `schema::Task` — it's derived from `(b+u)/(2d)` and rounded to 2 decimals on emit.
- `mutate.rs` — `rmap status` / `rmap mark` / `rmap depend` / `rmap new` paths. All four load with `toml_edit::DocumentMut` (NOT `toml::from_str`) to preserve comments/whitespace, mutate in place, then re-parse through `validate_tasks_str` to reject invalid mutations before the file is written. Bulk status: `update_status_many_str(path, input, ids, new_status)` walks the task array once, matches against a `HashSet`, fails atomically on any unknown ID (no partial write), and re-validates once at the end; `update_status_str` is a thin wrapper around the many-form. `update_markers_str(path, input, id, ops: &[MarkerOp])` walks a single task and applies `+marker`/`-marker` ops left-to-right; adds are idempotent (skip if present), removes are idempotent (skip if absent). `MarkerOp::parse` rejects tokens missing the `+`/`-` prefix. When `markers` was absent before the call and the op set produced a non-empty array, the affected task's keys are reordered into canonical position via `task.sort_values_by(canonical_task_key_index)` so the new `markers` field lands near the other small scalars rather than appended at the table's end. Idempotent or marker-already-present mutations do NOT trigger the sort — author-placed ordering for tasks that already declared `markers` is preserved. `add_dependency_str(path, input, id, in_repo: Option<&str>, cross_repo: Option<&CrossRepoSpec>)` appends to `depends_on` (in-repo) and/or `cross_repo` (array of inline tables); idempotent on the target id (in-repo) and on the `(repo, task_id, relation)` triple (cross-repo). Cycles, unknown ids, and invalid relations are rejected via post-edit re-validation. `CrossRepoSpec::parse` accepts `<repo>:<task_id>[:<relation>]` with relation defaulting to `"blocks"`. `add_task_str(path, input, &NewTaskFields) -> Result<(String, u32), MutateError>` appends a `[[task]]` to the document and returns `(updated_doc, allocated_id)`. `NewTaskFields::id = None` requests auto-allocation via the private `next_task_id(tasks)` helper, which walks the `[[task]]` array, extracts every numeric id via `Item::as_value().as_integer()`, and returns `max + 1` (or `1` if the array is empty); `TaskId::Text` ids are never auto-generated. Explicit ids that already exist are rejected as `MutateError::DuplicateId`. Lifecycle timestamps (`started_at`, `done_at`, `blocked_reason`, `shipped_in`) are absent from `NewTaskFields` on purpose — those transitions are owned by `rmap status` (and equivalent lifecycle mutators), not creation. Multi-task ingestion (e.g. `new --from-stdin` with multiple `[[task]]` blocks) chains calls and threads the returned string; the first failure aborts the batch and the file is byte-equal to its pre-call state.
- `next.rs` — pure selector: `next_tasks(tasks, filter, count) -> Vec<&Task>` returns up to `count` highest-Eff `pending` tasks whose `depends_on` are all `done`. `next_task` is a thin wrapper over `next_tasks(..., 1).into_iter().next()`. Takes `&TaskFilter` (shared with `query::list_tasks`) and honors `filter.marker` and `filter.bundle` only — `filter.status` is ignored (always implicitly `pending`) and `filter.phase` is ignored (focus comes from `[focus].phase`, not the user). Bundle filter applies BEFORE the focus partition, so `--bundle X` restricts the candidate pool first and focus only ranks within the bundle (AC: bundle wins over focus when both explicitly set). When `[focus].phase` is set, focus-phase candidates win over higher-Eff candidates in other phases; for `count > 1` the focus pool fills first (Eff desc, stable on ties) and the selector only falls back to other phases when the focus pool has fewer than `count` entries. Stable `sort_by` preserves TOML declaration order on Eff ties.
- `query.rs` — `rmap show` / `rmap list` read paths. `TaskFilter { status, marker, phase, bundle }` + `find_task` + `list_tasks` are pure; `format_task` / `format_task_row` produce human stdout. `matches_marker` and `matches_bundle` are `pub(crate)` so `next.rs` can reuse the same predicates. JSON output is delegated to `export.rs` so the agent-contract envelope stays consistent.
- `bundles.rs` — `rmap bundles` read path. `list_bundles(tasks, filter) -> Vec<BundleSummary>` and `BundleFilter { phase, has_next, in_focus }`. Per-bundle `next_task` is computed by `next::next_task` with a `TaskFilter { bundle: Some(name), .. }` — single source of truth for dep-satisfaction. Human rows: `<name>    <done>/<total> <glyph_or_next>  — <description>` under per-phase headers `phase <N> — <phase_name>  [<phase_status>{, focus}]`. Sort: focus-phase first, then `phase.order` asc, then `bundle.order` asc. JSON envelope is `{ schema_version, focus_phase, bundles }`; `focus_phase` serializes as explicit `null` when unset (deliberately not skipped). `status_counts` always zero-fills all four keys (`pending`, `in_progress`, `done`, `blocked`). `NextTaskSummary.eff` is `(efficiency * 100).round() / 100` matching `ExportedTask.eff`.
- `next_bundle.rs` — pure selector for `rmap next-bundle`. `pick(tasks, filter, today) -> Option<BundlePick<'a> { name, bundle, tasks }>` returns one session-sized bundle plus every actionable pending task in it, dep-topologically ordered. `NextBundleFilter { phase, bundle }` — `phase` overrides `[focus].phase`; `bundle` force-picks a specific bundle by name (bypasses ranking entirely; returns `None` when the name is not declared). Actionability is **broad**: a pending task T is actionable iff every dep is either `done` (anywhere) OR an in-bundle pending task that is itself broadly actionable (recursive, memoized DFS with `visiting` HashSet for cycle defense — `validate` already rejects cycles, defense is belt-and-suspenders). Ranking sorts candidates by `(in_focus_phase desc, sum_eff desc, bundle.order asc)`; bundles with zero actionable tasks are skipped. Topological emit uses Kahn's algorithm with stable Eff-desc priority for tiebreaks. Force-pick returns the bundle even when its actionable set is empty (`tasks` is `vec![]`); the caller distinguishes "missing bundle" (return `None`) from "zero-actionable" (return `Some` with empty tasks) and emits the appropriate stderr message. Reuses `query::matches_bundle` and `scoring::efficiency` — no duplicated dep-satisfaction logic. JSON envelope for `--json` is composed by `export::export_bundle_pick_json_str(tasks, effective_focus, pick)`: `{ schema_version, focus_phase, bundle: {name, phase, description} | null, tasks: [ExportedTask, ...] }`. `today` parameter mirrors `next::next_tasks` for future score-decay-sensitive ranking; unused today.
- `delegate.rs` — pure `rmap delegate` prompt formatter. It reads a task plus in-repo dependency context and emits structured Markdown for cloud agents; it never mutates files and never calls Linear/GitHub/Slack. `DelegateTarget` (the clap `ValueEnum`) lives here so `format_delegate_prompt` matches on the enum, not a stringified form — silent no-op risk on enum-variant addition is closed at the type level. `append_agent_notes(prompt, target)` emits a target-specific `## Environment notes` section mirroring `~/.claude/includes/cloud-agent-environments.md`. Section order in the emitted prompt is `## Context` → `## Task` → `## Acceptance criteria` → `## Out of scope` → `## Files to modify` → `## Scoring` → `## Environment notes` → `## Instructions`; the first seven are the agent contract enforced by `tests/delegate.rs::emits_canonical_section_order_with_distinguishing_line`. `## Context` always emits (carries `- Target:` / `- Project:` / `- Status:` / `- Phase:` / `- Bundle:` bullets plus optional `- Stored assignee:` / `- Markers:` / `- Linear:` / `- Shipped in:`, then optional `### Dependencies` and `### Cross-repo dependencies` sub-blocks); `## Scoring` always emits a single `[D:_/B:_/U:_ → Eff:_] <tier_glyph>` line; `## Files to modify` falls back to a one-bullet `{module}` line when `task.files_to_modify` is empty and `task.module` is `Some`, and is omitted entirely when both are empty.
- `diff.rs` — `rmap diff` engine. `diff_toml(base, current, verbose)` returns a `TomlDiff { metadata, tasks }` envelope (also `Serialize` for `--json`). `diff_metadata` walks scalar/optional/map fields (`schema_version`, `project`, `default_branch`, `linear.team_key`, `linear.workspace_url`, `phases.<key>`, `bundles.<key>`); `diff_tasks` walks the `[[task]]` array. Both emit `Added | Removed | Changed` granularity. Without `--verbose`, only the field-key set that drifted is surfaced (default — matches pre-11b shape). With `--verbose`, Changed entries gain a `values: [{field, before, after}]` array gated by `TASK_VERBOSE_WHITELIST` / `METADATA_VERBOSE_WHITELIST` — verbose values are `serde_json::Value` for shape-agnostic emission, and the array order follows the `diff_fields!` declaration order. `task_map` keys by `TaskId::Display`, so `Number(74)` and `Text("74")` collide across base/current (intentional — authors don't mix forms).
- `schema_json.rs` — emits a JSON Schema for `Tasks` via `schemars` derives on every type in `schema.rs`. The schema covers `tasks.toml` shape, not the `data.json` shape (which adds the computed `eff`).
- `scoring.rs` — shared `efficiency(&Task) -> f64`, `format_efficiency(f64) -> String`, and date helpers (`days_from_civil`, `days_since`, `score_decay_suffix`). All renderers and read commands import from here so the (b+u)/(2d) formula AND the staleness window have a single definition. Date math is pure-integer Howard Hinnant proleptic Gregorian — no chrono dependency.
- `stale.rs` — pure `parse_duration(input)` (parses `7d` / `2w` / `30d` / `1y`) and `find_stale(tasks, max_age_days, today)`. Filters in-progress tasks whose `started_at` is older than the threshold. No I/O.
- `doctor.rs` — `DoctorReport { ok, findings[], thresholds }` composite. Aggregates `validate::collect_findings`, `stale::find_stale`, score-decay, degenerate-bundle detection, missing-acceptance_criteria detection, and render drift. `--json` envelope tags variants with `kind: "validate" | "stale" | "score_decay" | "degenerate_bundle" | "missing_acceptance_criteria" | "drift"`. **Always exits 0** — informational only; the strict gates remain `validate` (exit 1) and `validate --check-render` (exit 2). Degenerate-bundle: a `[bundles.<name>]` whose task set equals every `[[task]]` with the same `phase` adds no information beyond the phase. Missing-AC: pending/in_progress tasks with `scores.d >= AC_DIFFICULTY_THRESHOLD (5)` OR `scores.b >= AC_BENEFIT_THRESHOLD (8)` and empty `acceptance_criteria`. The stale/score-decay cutoff (default 30d) and the missing-AC D/B bar (default 5/8) are CLI-overridable via `rmap doctor --threshold-days <N>` / `--ac-threshold <N>`; `DoctorThresholds::resolve` applies the constant defaults when a flag is absent, and the effective thresholds are echoed in the `--json` envelope (additive `thresholds` field). `--ac-threshold` collapses the distinct 5/8 defaults into a single `d >= N || b >= N` predicate; `--threshold-days` collapses the (coincidentally equal) stale and score-decay cutoffs into one knob.
- `paths.rs` — walks ancestors of `cwd` to find `roadmap/tasks.toml`. Project root is the directory containing `roadmap/`. CLI flags (`--tasks-path`, `--roadmap-path`, `--data-path`) override discovery.
- `main.rs` — `clap` derive CLI. Top-level `run()` returns `Result<ExitCode>`; specifically `--check-render` returns exit code **2 on render drift** (distinct from exit 1 on validation errors) so pre-commit hooks can distinguish "needs re-render" from "schema broken." `rmap diff` shells out to `git show <ref>:<repo-relative-path>` — diff is read-only on the working tree and a git repo. `rmap mark`'s `ops` positional uses `allow_hyphen_values = true` so `-parallel` is treated as a value, not a flag — as a consequence, named flags (`--tasks-path`, `--roadmap-path`, `--data-path`) must precede the positional `+x`/`-x` tokens on the command line. `rmap depend`'s `on` keyword is a literal optional positional; the runtime rejects anything other than `on` (or `None` when only `--cross-repo` is given). `rmap new` routes through `create_task(paths, from_stdin)`: with `--from-stdin`, stdin is parsed via a private `StdinPayload { task: Vec<StdinTask> }` shape (deny_unknown_fields) where `StdinTask::id` is `Option<TaskId>` — `schema::Task::id` is required, so the dedicated shape is what lets the auto-id path accept payloads that omit `id`. `status` is NOT a `StdinTask` field — creation always emits `"pending"`; lifecycle transitions belong to `rmap status`. Without `--from-stdin`, `prompt_task_fields(&existing_tasks)` drives a `dialoguer` flow (phase → bundle → title → D/B/U → markers → acceptance criteria → assignee → linear_id → module); a non-TTY stdin aborts with a "use `--from-stdin`" message before any prompt is drawn. Both paths call `add_task_str` per task and only write `tasks.toml` after the loop validates cleanly — atomic for multi-task fragments.

## Load-bearing invariants

These are easy to violate without breaking tests immediately:

- **Marker boundaries are byte-preserved.** `render` only rewrites bytes between matched `<!-- TASKS:BEGIN phase=N -->` and `<!-- TASKS:END -->`. Everything else — including hand-edited prose, blank lines, the marker lines themselves — is byte-equal in/out. Don't "normalize" the input string anywhere in `render.rs`.
- **FOCUS markers follow the same byte-preservation rule.** `<!-- FOCUS:BEGIN -->` / `<!-- FOCUS:END -->` is the optional second marker pair the renderer recognizes. The pair has no `phase=N` parameter — only one is expected per file, and only the first is replaced (later pairs are left untouched). Zero-config default: absence of the markers means no FOCUS block is rendered. Today-sensitivity (the 7-day shipped window) is consistent with score-decay rendering — `validate --check-render` will report drift when the day-window flips, the same way it already does for `?` decay suffixes. Don't change the marker spelling, the line shape (`**Focus phase:** ...`, `**Last shipped:** ...`, `**Up next:** Task C — <title> [D/B/U → Eff] <tier_glyph>`), or the empty-state strings (`no recent shipments` / `none — focus phase complete or all blocked`) without bumping `schema_version` — those strings are part of what agents grep for. The tier glyph on Up next is render-only and absent from the empty-state line (no Eff value means no glyph).
- **MERMAID markers follow the same byte-preservation rule.** `<!-- MERMAID:BEGIN -->` / `<!-- MERMAID:END -->` is the optional third marker pair. No `phase=N` parameter; one pair per file; only the first is replaced. Zero-config default: absence of the markers means no mermaid block is rendered. The body shape is part of the contract: ```` ```mermaid ```` fence → `gantt\n    title <project>\n    dateFormat YYYY-MM-DD` → per-phase `section Phase N — <name>` (sorted by `phases[*].order`) → per-row `<title> :<done|active|crit>, <started_at>, <end>` for tasks with `started_at`. Empty-state row: `%% no tasks with started_at yet`. `validate --check-render` automatically catches drift in this block — same exit-2 contract as TASKS/FOCUS. Today-sensitivity flows through `today_iso()` (in-progress and blocked rows end at "today"); the `?` decay convention does NOT apply to the mermaid block. Don't change the marker spelling, the fence language tag (`mermaid`), or the status keywords (`done`/`active`/`crit`) without bumping `schema_version`.
- **`eff` is never persisted.** Don't add it to `schema::Task`. Recompute at render/export time. The schema struct has `#[serde(deny_unknown_fields)]` and would reject it on load anyway.
- **Mutations go through `toml_edit`, not `toml`.** `toml::from_str` + `to_string` would strip comments and reflow formatting. `mutate.rs` uses `DocumentMut` for this reason. New mutator commands (Phase 4+) must do the same.
- **`schema_version = 1` is required.** Refuse to render unknown versions; `validate.rs` emits a `rmap migrate` hint. Bump on any breaking schema change.
- **`linear_id` validation is conditional.** If the `[linear]` table is absent, `linear_id` format is not checked — Linear is opt-in per project.
- **Status / marker / relation enums live as `&[&str]` constants in `validate.rs`** (`VALID_STATUSES`, `VALID_MARKERS`, `VALID_CROSS_REPO_RELATIONS`). Any new value must also be added to the render-time match arms in `render.rs` (status symbols, marker suffixes) — they don't share a source.
- **D/B/U score range is `1..=10`.** `validate::validate_scores` enforces `MIN_SCORE = 1` / `MAX_SCORE = 10` on each of `task.scores.{d,b,u}`, matching the rubric in `task-prioritization.md`. The error message — `task <id> scores.<field> = <value> must be in 1..=10` — is part of the agent-grep contract; the `1..=10` substring is what agents and pre-commit hooks pattern-match against, so changing the bounds (or the spelling of the range) is a `schema_version` bump. `Scores` itself stays `u32`-per-field: TOML's `u32` decode already rejects negatives, the range check enforces the application-level rubric on top of that, and there is no need for `Option<u32>` or signed types. The check runs in both `validate_tasks_str` (short-circuiting) and `collect_findings` (accumulating across distinct validators), so `rmap validate` (exit 1) and `rmap doctor` both surface offending scores.
- **`schema --json` is the agent self-description boundary (Phase 8).** The schema comes from `schemars` derives on the live `schema::Tasks` types — adding a `#[serde]` rename or a new field changes the schema automatically. Don't hand-author a parallel schema. The CI test `schema_json_command_emits_parseable_schema_for_tasks_file` validates the example `tasks.toml` against the emitted schema; it fails loudly if derive output drifts from serialize output.
- **`--json` outputs of `show` / `list` / `next` / `schema` / `diff` are the agent contract.** Add fields freely; never rename or remove without a `schema_version` bump.
- **`delegate` is read-only and agent-targeted.** It emits Markdown because humans transport the prompt to cloud agents, but the zielgruppe is the target agent. `--to` is an explicit routing override; any stored `assignee` is context, not an enforcement gate.
- **`rmap diff --against` defaults to `current.default_branch`.** Explicit `--against <ref>` overrides. Don't hardcode `"main"`; the loaded TOML is the source of truth for branch naming.
- **`diff::task_changes` per-field comparison is hand-maintained.** When you add a field to `schema::Task`, also add it to the `diff_fields!` invocation in `diff::task_changes` AND to `export::ExportedTask` — otherwise `rmap diff` silently misses the field and `rmap show --json` / `list --json` won't surface it. The macro consolidates the comparisons into one list but is not auto-derived; touch all three files in the same commit when extending `Task`. Decide consciously whether the new field belongs on `TASK_VERBOSE_WHITELIST` in `diff.rs` — whitelist membership is part of the `rmap diff --verbose` agent contract.
- **`rmap diff --verbose` is additive.** Without `--verbose`, `diff` JSON output is byte-identical to pre-11b releases (no `values` key anywhere). With `--verbose`, Changed entries gain `values: [{field, before, after}]` filtered by `TASK_VERBOSE_WHITELIST` / `METADATA_VERBOSE_WHITELIST`. Added/Removed entries always have `values: null` (skipped on serialize). Renaming or removing a whitelist member is a breaking change to the agent contract — bump `schema_version` first.
- **`rmap delegate`'s per-agent footer mirrors `~/.claude/includes/cloud-agent-environments.md`.** That skill include is the source of truth for what Codex/Cursor can reach. `delegate.rs::append_agent_notes` holds inline string literals — when the skill changes (e.g. Codex sandbox gains a new constraint), sync the bullets manually. Tests in `tests/delegate.rs` only assert presence of section header + one target-distinguishing phrase, so phrasing tweaks are safe; structural removal will fail loudly. The same "header + one distinguishing line" pattern locks in the seven canonical `##` sections (`Context` → `Task` → `Acceptance criteria` → `Out of scope` → `Files to modify` → `Scoring` → `Environment notes`) via `emits_canonical_section_order_with_distinguishing_line`; renaming, reordering, or dropping any of those headers — or changing the `## Scoring` body shape `[D:_/B:_/U:_ → Eff:_] <glyph>` — is a `schema_version` bump.
- **Top-level `Tasks` fields have the same three-place contract as `Task` fields.** When you add a top-level field to `schema::Tasks` (e.g. `focus`), also extend `diff::diff_metadata` (so `rmap diff` notices add/remove/change) AND `export::ExportedTasks` (so `data.json` surfaces it). The Task-level macro doesn't cover top-level fields; they're walked by hand in `diff_metadata`. Same three-file edit discipline applies.
- **Timestamp fields validate by shape, not semantics.** `created_at`, `started_at`, `done_at`, and `scored_at` are all `Option<String>` validated against the `YYYY-MM-DD` shape (10 chars: 4 digits, dash, 2 digits, dash, 2 digits). Don't promote them to a typed `Date` — the value lives next to user-edited TOML where exact string preservation matters. `9999-99-99` passes the validator on purpose; the error message wording reflects this (it says "must match YYYY-MM-DD format", not "must be an ISO-8601 date").
- **`blocked_reason` is conditionally required.** Whenever `status = "blocked"`, `blocked_reason` must be `Some`. The mutator path (`rmap status <id> blocked`) re-runs validation, so flipping a task to `blocked` without a reason will fail to write.
- **`today_iso()` is the single source of truth for "now".** Reads `RMAP_TODAY` env var first (for deterministic tests), then falls back to `SystemTime::now()`. Any code path that needs today's date — score-decay rendering, `stale`, `doctor` — calls this helper. Tests that exercise date-sensitive behavior MUST set `RMAP_TODAY` on the `Command` env (via `.env("RMAP_TODAY", ...)` on the `Command` builder, or `today.txt` next to the fixture for golden tests). Don't read the system clock directly in new code.
- **`rmap doctor` always exits 0 on success.** It is the soft-signal aggregator, not a gate. The strict gates are `rmap validate` (exit 1 on schema error) and `rmap validate --check-render` (exit 2 on render drift). Doctor only propagates a non-zero exit when `tasks.toml` is fundamentally unparseable — i.e., there is nothing to analyze. CI hooks that want to fail on doctor findings should pipe through jq: `rmap doctor --json | jq -e '.findings | length == 0'`.
- **`DoctorFinding`'s `kind` strings are part of the agent contract.** `validate`, `stale`, `score_decay`, `drift` — same additive rule as `show --json` / `list --json` / `next --json`. Renaming a `kind` value requires a `schema_version` bump. Adding a new variant is fine.
- **Bulk `rmap status 1,2,3 done` is atomic.** All listed IDs must resolve OR no file write happens. The behavior is enforced by validating once at the end of `update_status_many_str` and refusing to emit a partial document. Don't add a "best effort" flag without explicit user request — atomicity is the value proposition over a shell loop.
- **All mutators inherit the validate-then-write contract.** `update_status_*`, `update_markers_str`, `add_dependency_str`, and `add_task_str` each end with `validate_tasks_str(path, &output)?` BEFORE returning the new string to the caller. The binary then re-parses and re-renders before any file is written. Future mutators (anything else in Phase 11b/12) must follow the same shape — never `std::fs::write` the output of a `toml_edit` mutation without round-tripping through `validate_tasks_str` first. The whole point of these helpers is that an invalid mutation (cycle, unknown id, bad marker, bad relation, duplicate id, unknown phase/bundle on creation) errors with the file byte-equal to its pre-mutation state.
- **`rmap mark` is the only mutator that auto-sorts task keys; this is by design.** When `update_markers_str` inserts a `markers` field on a task that didn't have one, it calls `task.sort_values_by(canonical_task_key_index)` so the new field lands near the other small scalars instead of being appended after multi-line entries like `acceptance_criteria`. `add_dependency_str` (depends_on, cross_repo) and `update_status_str` do NOT auto-sort — those fields' natural placement is fine, and reordering existing keys without a strong reason erodes author intent. If a second consumer reports a similar cosmetic complaint about `depend`, factor the sort call up; until then, the helper is `mark`-only. The canonical order in `canonical_task_key_index` mirrors `add_task_str`'s write order — keep them in sync.
- **`rmap new` auto-allocates numeric ids only.** `next_task_id(tasks)` walks the `[[task]]` array, considers only `TaskId::Number(n)` entries, and returns `max(n) + 1` (or `1` if the array is empty). Text ids (`TaskId::Text("78b")`) are never auto-generated — if a project starts mixing numeric and text ids, only the numeric subset participates in allocation. Multi-task stdin payloads that omit `id` get sequential allocations (max+1, max+2, …) as the loop runs; explicit ids may be freely interleaved with auto ids in the same payload. Duplicate explicit ids fail with `MutateError::DuplicateId` before any write.
- **Lifecycle timestamps are NOT settable on creation.** `started_at`, `done_at`, `blocked_reason`, and `shipped_in` are deliberately absent from `NewTaskFields` and from the `StdinTask` deserialization shape. Those fields encode state transitions (work started, work finished, blocker recorded, release tagged); the create surface must produce tasks in the `pending` lifecycle phase only. `rmap status` (and equivalent transition mutators) owns those edits. Don't add lifecycle fields to `NewTaskFields` without thinking through what it means for an agent to create an already-done task — almost certainly the wrong shape.
- **Eff tier glyph is centralized in `scoring::tier_glyph`.** The thresholds — `>= 2.0 → 🎯`, `>= 1.5 → 🚀`, `>= 1.0 → 📋`, else `⚠️` — are the agent-grep contract; the glyph spellings are part of `SKILLS.md` / `task-prioritization.md` and changing any of them is a `schema_version` bump. Every Eff render surface calls `tier_glyph(eff)` after `format_efficiency`: TASKS-table row, FOCUS Up next line, `rmap show` scores line, `rmap list` row, `rmap next` row, `rmap delegate` scores line. Glyph placement: outside brackets where they exist (`[D/B/U → Eff:X.Y] 🚀`), space-separated after the value where they don't (delegate, show). NEVER fold the glyph into `format_efficiency` itself — `data.json` / `show --json` / `list --json` / `next --json` / `diff --json` payloads must stay numeric. The glyph is a render-time concatenation only.
- **`rmap bundles` row shape and status-glyph rules are the agent contract.** The five-branch `status_glyph_or_next` ladder — (1) all-done → `✅` (vacuously fires on empty bundles, by design); (2) `pending == 0 && in_progress > 0` → `🚧`; (3) `pending == 0 && in_progress == 0 && blocked > 0` → `all-blocked ⛔`; (4) `pending > 0 && next_task.is_none()` → `pending:<n> (deps unmet) ⏸`; (5) otherwise → `next:<id> [Eff:<x.y>] <tier_glyph>` — and the row separator pattern (`  <name>    <done>/<total> <glyph_or_next>  — <description>`, with two-space indent, four spaces between name and count, single space before the glyph, two spaces before the em-dash) are what agents grep for. Renaming a glyph, changing separator spacing, reordering or removing a branch is a `schema_version` bump. Glyph thresholds come from `scoring::tier_glyph` — never fold the glyph into `format_efficiency` (mirrors the existing Eff tier glyph invariant). `BundleSummary.next_task` reuses `next::next_task` with a bundle-restricted `TaskFilter` — do NOT duplicate dep-satisfaction logic. JSON envelope: `focus_phase` is emitted as explicit `null` when unset (not skipped), `status_counts` always zero-fills all four keys.
- **`rmap next --count` JSON shape is split by N.** `--count 1` (the default) emits a bare `ExportedTask` object or `null` — byte-identical to pre-Task-15 releases. `--count N` for any `N > 1` emits a JSON array `[ExportedTask, ...]` (possibly `[]` when nothing is eligible). Human output prints one line per task in both cases (zero lines when empty). The shape split is reachable only via explicit `--count >1`, so the agent contract for default invocation is preserved. `--count 0` is rejected at clap parse time via `NonZeroUsize`. Renaming the flag, changing the default, dropping the `NonZeroUsize` guard, or flipping `--count 1` to always emit an array is a `schema_version` bump. The selector helper for the array branch is `export::export_tasks_array_json_str` — it returns a bare array, NOT the `ExportedTasks` envelope used by `rmap render` / `rmap list --json` (no `schema_version` / `project` / `phases` / `bundles` wrapper).
- **`rmap next-bundle` ranking rule, empty-state spellings, and JSON envelope are the agent contract.** Ranking precedence is `(in_focus_phase desc, sum_eff desc, bundle.order asc)` — changing the order is a `schema_version` bump. Three empty-state spellings, each load-bearing: (1) no `--bundle`, no actionable bundle anywhere → stderr `none — no actionable bundle in any phase` (exit 0); (2) no `--bundle`, focus set, no actionable bundle in focus phase → stderr `none — no actionable bundle in phase N` (exit 0); (3) `--bundle X` where X is declared but zero-actionable → stderr `none — bundle '<X>' has no actionable pending tasks` (exit 0). The fourth case — `--bundle X` where X is not declared in `[bundles.*]` — is a hard error (exit 1, stderr `bundle '<X>' is not declared in tasks.toml`). Empty-state lines go to **stderr** with empty stdout; the distinction matters for scripted pipelines that consume stdout. Actionability is **broad** (in-bundle pending deps satisfy if themselves actionable); narrowing to strict (all deps `done`) would change which bundles surface and is a `schema_version` bump. **No D-budget subsetting** — the selector emits every actionable task in the bundle regardless of cumulative D; oversized bundles are an author-time issue (split in `tasks.toml`). JSON envelope shape: `{ schema_version, focus_phase, bundle: {name, phase, description} | null, tasks: [ExportedTask, ...] }`; `focus_phase` is the **effective** focus (post-`--phase` override), not the stored `[focus].phase`. Empty pick emits `bundle: null, tasks: []` in the same envelope (NOT a separate `null` literal — mirrors `rmap bundles --json` rather than `rmap next --json`). Topological ordering of `tasks` is observable via `--json` and locked in by `next_bundle_emits_topological_order_within_bundle`. Force-pick (`--bundle X`) bypasses ranking entirely, including the focus-phase preference, and including `--phase N` (when both are passed, `--bundle` wins silently — more-specific flag, Unix convention).
- **Archive collapse on `phases.N.status = "done"`.** `render_phase_table` short-circuits when the matching phase entry exists and its status is `"done"`: the TASKS:BEGIN body collapses to a single line `> N task(s). See [CHANGELOG.md](CHANGELOG.md#phase-N-<slug>).` — noun is `task` when `N == 1`, `tasks` otherwise. `N` is the per-phase task count; `slug = phase_slug(phase.name)` (lowercased, split on `!c.is_alphanumeric()`, empty segments dropped, joined with `-`). Marker boundaries stay byte-preserved. Per-phase scoped — non-done phases in the same file continue to render the full task table; the collapse is unconditional with no per-phase opt-out today (`archive = false` deferred until a real consumer asks). The line shape is what agents grep for and what `validate --check-render` locks in — changing it requires a `schema_version` bump.

## Tests

- `tests/cli.rs` — black-box CLI tests via `Command::new(env!("CARGO_BIN_EXE_rmap"))`. Each test gets a unique temp dir from a per-test atomic counter. Date-sensitive tests set `RMAP_TODAY` on the `Command` env (e.g. `.env("RMAP_TODAY", "2026-05-11")`).
- `tests/skills_smoke.rs` + `tests/skills_fixture/` — parses every fenced ```bash``` block in `SKILLS.md`, extracts the optional `# exit: <N>` annotation (default 0), and runs each `rmap ` invocation in a fresh fixture copy with `RMAP_TODAY=2026-05-12` pinned. Setup runs `rmap render` first (idempotent — produces `ROADMAP.md` + `data.json`) then `git init -b main && commit` so `rmap diff` has a base ref. The smoke test is the agent-contract gate for `SKILLS.md` — adding a command to the doc means its exit code is locked in; renaming or removing a documented command requires updating both `SKILLS.md` and the fixture in the same commit.
- `tests/golden/<case>/` — fixture pairs: `tasks.toml`, `ROADMAP.input.md` (input), `ROADMAP.md` (expected output). Adding a case = drop in a triplet; `tests/render.rs` picks it up. Render-template changes that break expected output fail loudly — that's intended. Optional `today.txt` next to the fixture pins the render date for the runner (otherwise it uses `today_iso()`). Add a `today.txt` to any fixture that uses `scored_at` so it doesn't drift into score-decay over time.
- `tests/roundtrip.rs` — Phase 4 lookahead: parse → `toml_edit` round-trip → assert no spurious diff. Catches comment-preservation regressions before mutation code expands.

## Scope discipline

`ROADMAP.md` (rendered from `roadmap/tasks.toml`) tracks open phases; `DESIGN.md` carries the design contract and out-of-scope list; `CHANGELOG.md` is the shipped-phase record. Implemented today: validate, render, export json, status (single + bulk), mark, depend, new (interactive + `--from-stdin`), next, show, list, bundles, schema, diff, delegate, stale, doctor. Score-decay rendering is automatic on tasks with `scored_at` >30d or missing. Deliberately out of scope (per `DESIGN.md`): Linear API calls, web server, git integration beyond `git show <ref>:<path>` for `rmap diff`, shell completions, CI workflow, multi-user sync. Don't add these without checking the roadmap first.
